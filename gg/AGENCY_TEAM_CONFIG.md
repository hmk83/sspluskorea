# AGENCY_TEAM_CONFIG

## 목적

이 문서는 `프롬프트제작 사이트`를 서비스와 홈페이지 관점에서 기획, 디자인, 퍼블리싱, 프론트엔드, 백엔드, 검수까지 일관되게 만들기 위한 최정예 에이전시 운영 기준이다.

모든 작업은 단순 화면 제작이 아니라 실제 사용자가 프롬프트를 만들고, 저장하고, 다시 활용하며, 서비스의 신뢰도를 느끼는 전체 흐름을 기준으로 판단한다.

## 운영 원칙

1. 사용 목적이 먼저다.
   - 사용자가 무엇을 만들고 싶은지, 어떤 결과물을 얻어야 하는지부터 정의한다.
   - 기능명보다 사용자 행동, 입력값, 결과물, 재사용 흐름을 우선한다.

2. 모바일 품질을 기본값으로 둔다.
   - 모든 화면은 모바일에서 먼저 읽히고 조작되어야 한다.
   - 데스크톱은 확장 경험으로 설계하고, 모바일은 축소판이 아니라 완성된 기본 경험으로 본다.

3. 홈페이지와 서비스 화면을 분리해서 판단한다.
   - 홈페이지는 이해, 신뢰, 진입을 담당한다.
   - 서비스 화면은 생성, 편집, 저장, 복사, 관리, 재사용을 담당한다.

4. 검수는 마지막 단계가 아니라 전 과정에 참여한다.
   - 기획 단계에서 검수 기준을 먼저 만든다.
   - 구현 후에는 화면, 데이터, 반응형, 오류 상태, 실제 사용 시나리오까지 확인한다.

5. 애매한 문구와 애매한 기능은 출시하지 않는다.
   - 버튼명, 입력 안내, 오류 메시지, 결과 안내는 사용자가 다음 행동을 바로 알 수 있어야 한다.
   - 내부 용어를 그대로 노출하지 않는다.

## 팀 구성

### 1. 서비스 및 홈페이지 기획팀

**역할**

- 서비스의 핵심 목적, 사용자 여정, 기능 우선순위, 홈페이지 구조를 설계한다.
- 홈페이지 방문자가 서비스의 가치를 빠르게 이해하고 실제 제작 화면으로 진입하도록 흐름을 만든다.
- 프롬프트 제작, 템플릿 선택, 결과 저장, 복사, 재활용 흐름을 명확하게 정의한다.

**담당 범위**

- 서비스 콘셉트와 핵심 사용자 정의
- 홈페이지 정보 구조
- 서비스 메뉴 구조
- 사용자 시나리오
- 기능 우선순위
- 화면별 목적 정의
- CTA 문구와 버튼 흐름
- 오류, 빈 상태, 저장 완료, 생성 완료 등 상태 문구

**필수 산출물**

- 페이지 구조도
- 사용자 흐름표
- 화면별 기능 정의
- 주요 CTA 문구
- 핵심 사용 시나리오
- 출시 범위와 후순위 범위

**검토 기준**

- 사용자가 첫 화면에서 무엇을 할 수 있는지 즉시 이해하는가
- 홈페이지에서 서비스 화면으로 자연스럽게 진입하는가
- 프롬프트 제작 결과물이 사용자의 실제 업무에 재사용 가능한가
- 기능 흐름 중 막히는 지점이 없는가

### 2. UX/UI 디자인팀

**역할**

- 서비스와 홈페이지의 시각 체계, 화면 레이아웃, 인터랙션 패턴을 설계한다.
- 프롬프트 제작 도구가 복잡해 보이지 않으면서도 전문적으로 느껴지도록 만든다.
- 모바일, 태블릿, 데스크톱별 화면 밀도와 조작 편의성을 조정한다.

**담당 범위**

- 디자인 시스템
- 컬러, 폰트, 간격, 버튼, 폼, 카드, 모달 규칙
- 홈페이지 비주얼 방향
- 서비스 화면 UI
- 생성 결과 영역 디자인
- 저장 목록, 템플릿 목록, 편집 화면 디자인
- 모바일 터치 영역과 스크롤 흐름

**필수 산출물**

- 주요 화면 디자인
- 모바일 화면 디자인
- 컴포넌트 스타일 규칙
- 빈 상태와 오류 상태 디자인
- 결과물 카드와 복사/저장 UI
- 반응형 레이아웃 기준

**검토 기준**

- 중요한 행동 버튼이 화면에서 명확히 보이는가
- 입력 영역과 결과 영역이 헷갈리지 않는가
- 모바일에서 터치 영역이 충분한가
- 카드, 버튼, 폼이 과하게 장식적이지 않고 실제 작업에 집중되는가

### 3. 퍼블리싱 및 모바일 최적화팀

**역할**

- 디자인을 실제 HTML/CSS 구조로 정확하게 구현하고 모바일 최적화를 책임진다.
- 화면 깨짐, 텍스트 넘침, 터치 불편, 스크롤 문제, 헤더 고정 문제를 잡는다.
- 브라우저별 기본 동작 차이를 확인한다.

**담당 범위**

- 반응형 HTML/CSS 구현
- 모바일 우선 레이아웃
- 버튼, 입력창, 탭, 드롭다운, 모달 퍼블리싱
- 접근성 기본 구조
- 이미지와 아이콘 최적화
- 텍스트 줄바꿈과 긴 문장 대응
- iOS Safari, Android Chrome 대응

**필수 산출물**

- 모바일 최적화된 퍼블리싱 화면
- 주요 해상도별 레이아웃 확인
- 터치 영역 점검
- 텍스트 넘침 점검
- 접근성 기본 체크

**검토 기준**

- 360px 폭에서도 핵심 기능을 사용할 수 있는가
- 긴 버튼명과 긴 결과 문장이 UI를 깨뜨리지 않는가
- 고정 헤더나 하단 버튼이 콘텐츠를 가리지 않는가
- 입력, 복사, 저장, 다시 만들기 흐름이 모바일에서 불편하지 않은가

### 4. 프론트엔드 개발팀

**역할**

- 사용자가 직접 조작하는 기능과 상태 관리를 구현한다.
- 프롬프트 생성, 템플릿 선택, 결과 편집, 복사, 저장, 목록 관리 등 프론트 기능을 책임진다.
- 백엔드 API와 안정적으로 연결하고 로딩, 실패, 재시도 상태를 만든다.

**담당 범위**

- 화면 라우팅
- 상태 관리
- 프롬프트 입력 폼
- 템플릿 선택 UI
- 생성 결과 표시
- 결과 편집
- 복사, 저장, 삭제, 즐겨찾기
- API 연동
- 로딩, 오류, 빈 상태 처리
- 클라이언트 검증

**필수 산출물**

- 실제 동작 가능한 서비스 화면
- API 연동 코드
- 상태별 UI
- 폼 검증
- 재사용 가능한 컴포넌트
- 기본 프론트엔드 테스트 또는 수동 검수 시나리오

**검토 기준**

- 생성 버튼을 눌렀을 때 중복 요청이 발생하지 않는가
- 실패 시 사용자가 다시 시도할 수 있는가
- 저장된 결과가 목록에서 정확히 보이는가
- 새로고침, 뒤로가기, 모바일 키보드 상황에서도 흐름이 깨지지 않는가

### 5. 백엔드 개발팀

**역할**

- 서비스 데이터, 사용자 정보, 프롬프트 생성 요청, 저장 결과, 템플릿 관리, 권한 처리를 책임진다.
- 프론트엔드가 안정적으로 사용할 수 있는 API와 데이터 구조를 제공한다.
- 보안, 비용, 속도, 장애 대응을 함께 고려한다.

**담당 범위**

- API 설계
- 데이터 모델링
- 사용자 인증과 권한
- 프롬프트 생성 요청 처리
- 결과 저장과 조회
- 템플릿 관리
- 사용량 제한
- 로그와 오류 추적
- 데이터 백업 기준
- 관리자 기능 기반

**필수 산출물**

- API 명세
- 데이터 스키마
- 인증/권한 정책
- 생성 요청 처리 로직
- 저장/조회/삭제 API
- 오류 코드와 메시지 기준
- 운영 로그 기준

**검토 기준**

- 프론트엔드가 필요한 데이터를 과하거나 부족하지 않게 받는가
- 실패 응답이 명확하고 복구 가능한가
- 사용자의 저장 결과가 다른 사용자에게 노출되지 않는가
- 과도한 생성 요청, 중복 저장, 비정상 입력을 방어하는가

### 6. 검수 및 QA팀

**역할**

- 기획, 디자인, 퍼블리싱, 프론트엔드, 백엔드가 실제 사용자 경험으로 맞물리는지 검수한다.
- 단순 오류 확인이 아니라 서비스 목적, 문구, 모바일 조작, 데이터 정합성, 예외 상황을 함께 본다.
- 출시 가능 여부를 최종 판단한다.

**담당 범위**

- 기능 검수
- 모바일 검수
- 문구 검수
- 반응형 검수
- 저장/조회 데이터 검수
- API 오류 상태 검수
- 브라우저 호환성 검수
- 사용자 시나리오 검수
- 회귀 검수

**필수 산출물**

- 검수 체크리스트
- 발견 이슈 목록
- 재현 경로
- 우선순위
- 수정 확인 결과
- 출시 가능 여부 보고

**검토 기준**

- 신규 사용자가 설명 없이 핵심 기능을 완료할 수 있는가
- 모바일에서 생성, 복사, 저장이 모두 가능한가
- 생성 결과가 사라지거나 잘못 저장되는 경우가 없는가
- 실패, 빈 상태, 로딩 상태가 모두 준비되어 있는가
- 수정 후 같은 문제가 다시 생기지 않도록 기준이 남았는가

## 기본 제작 프로세스

1. 요구 정의
   - 만들 화면, 사용자 목적, 성공 조건, 제외 범위를 정한다.

2. 기획 검토
   - 페이지 구조, 기능 흐름, 문구, 예외 상태를 먼저 확정한다.

3. 디자인 설계
   - 모바일과 데스크톱 화면을 함께 설계한다.

4. 퍼블리싱 구현
   - 디자인을 반응형 구조로 구현하고 모바일 조작성을 점검한다.

5. 프론트엔드 구현
   - 실제 화면 상태, 입력, 결과, 저장, API 연결을 구현한다.

6. 백엔드 구현
   - 필요한 API, 데이터 저장, 인증, 사용량 제한, 오류 응답을 구현한다.

7. 통합 검수
   - 사용자 시나리오 기준으로 처음부터 끝까지 확인한다.

8. 출시 판단
   - 치명, 중요, 보통, 개선 이슈로 나누고 출시 가능 여부를 결정한다.

## 공통 Definition of Done

작업은 아래 조건을 만족해야 완료로 본다.

- 모바일에서 핵심 시나리오가 끝까지 동작한다.
- 데스크톱에서 레이아웃이 과하게 비거나 깨지지 않는다.
- 텍스트가 버튼, 카드, 입력창 밖으로 넘치지 않는다.
- 로딩, 성공, 실패, 빈 상태가 존재한다.
- 저장 데이터와 화면 표시 데이터가 일치한다.
- 사용자가 다음 행동을 알 수 있는 문구가 제공된다.
- 같은 오류가 반복되지 않도록 원인과 방지 기준이 남는다.
- 검수팀이 재현 경로와 완료 여부를 확인했다.

## 우선순위 기준

### P0 출시 불가

- 생성, 저장, 조회, 로그인 등 핵심 기능이 동작하지 않음
- 사용자 데이터가 잘못 저장되거나 노출됨
- 모바일에서 핵심 기능을 사용할 수 없음
- 결제나 권한이 잘못 처리됨

### P1 출시 전 수정

- 주요 버튼이나 입력 흐름이 헷갈림
- 특정 해상도에서 화면이 깨짐
- 오류 상태에서 사용자가 복구할 수 없음
- 저장 결과가 목록과 상세에서 다르게 보임

### P2 출시 후 개선 가능

- 문구가 더 명확해질 필요가 있음
- 일부 여백, 정렬, 애니메이션이 덜 다듬어짐
- 부가 기능의 사용성이 부족함

## 에이전시 기본 선언

앞으로 `프롬프트제작 사이트` 작업에서는 이 문서를 기준으로 필요한 팀을 호출한다.

요청이 단순 수정처럼 보여도 서비스 흐름, 모바일 품질, 데이터 정합성, 검수 기준에 영향을 주면 해당 팀의 관점까지 함께 반영한다.
